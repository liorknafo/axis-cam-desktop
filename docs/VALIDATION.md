## Sign in with ChatGPT

- Verified against a loopback stand-in for OpenAI's servers; no test that runs contacts OpenAI or the Keychain (the one Keychain test is ignored).
- First sign-in registers the app, exchanges the code with PKCE and validates the ID token (RS256 signature, issuer, audience, expiry, nonce). Wrong state, denial, timeout and each invalid token are refused.
- Tokens refresh before expiry and once after a 401, one refresh at a time, saved before use; fatal refresh errors and sign-out clear the saved sign-in. Before refreshing, the client reads the store again: a sign-in for the same account that another copy has already refreshed is adopted without a refresh request (two clients on one store make one token request), and it is refreshed with its own token only when it is itself near expiry. After a fatal refresh, a newer saved sign-in for the same account is used instead of being deleted, and another user's is not adopted. A saved set is adopted only when it expires later than the client's own and holds no refresh token the client has spent: when both saves of a refresh fail, the next expiry-driven refresh sends the rotated refresh-2, not the spent refresh-1 left in the store; a stored refresh-2 set that outlives the client's refresh-3 set is not adopted once refresh-2 is spent; and after a fatal refresh an older saved set is neither adopted nor deleted. The client reports a refresh in flight from before its request until after its save, also while OpenAI has not answered yet (the close decision reads this). It also reports a refresh in its save, from OpenAI's answer until after the save, and not while the request is still out. The delete a close starts when it stops waiting for a sign-out marks that client's sign-in abandoned under the lock a refresh's save takes: a refresh whose request was still out when the delete ran finishes and uses its tokens, but its save writes nothing and the store stays empty (checked in review: with the flag check removed, the test fails with the refreshed sign-in saved).
- Streamed replies require completion; failures, refusals, early ends and each plan-usage error map to a clear state. Unsupported structured output falls back to plain JSON once. A reply larger than 4 MB is refused, and a refusal is shown as one line of at most 300 characters.
- Tokens never appear in settings or Debug output, and the account state the UI shows holds only the name, the email and whether plan usage is granted.
- Live check with the user's account (3 October 2026; not a test): the first attempt was rejected because the installation ID was not in `urn:uuid:` form. After matching OpenAI's reference kit (ID format, `/auth/callback`, client ID and `azp` checks), registration and browser approval succeeded.

## AI planner

- Verified with a scripted stand-in for the model, and for the OpenAI backend with the loopback stand-in; no test contacts OpenAI. A live planning run needs the user's ChatGPT sign-in and is not part of this evidence.
- The OpenAI backend sends the whole conversation (system, user, assistant, user) with the plan schema, and once the plan route has refused structured output it asks for plain JSON at once.
- A good first proposal gets one coverage round, and the passing plan with the larger exposed share is kept; a first plan that leaves nothing covered makes one request. ## Continuous stock and adaptive meshing

- Flat and ball cutter implicit fields are compared against an independent swept-solid membership calculation for horizontal strokes, ascending/descending ramps and vertical entries. Tests include finite flute extent and rotated/translated setup frames.
- Adaptive octree / manifold dual contouring produces triangle surfaces directly from continuous cutter history; the old occupancy grid no longer supplies rendered voxel faces. - Closing: the workspace is saved first, and the window stays when it cannot be. A pending sign-out, sign-in save or refresh of the sign-in (from before its request until after its save) is waited for, at most 10 seconds (a repeated request keeps the first time; the window closes when signing out ends, when the sign-in save reports, saved or not, when the refresh ends, checked on Tick, or when the time is up). A sign-out still pending at the end of the wait starts deleting the saved sign-in on the blocking pool before the window closes, through the signing-out client so that its refresh cannot save the sign-in again; a delete started just before a Tokio runtime is dropped still completes. With nothing pending and a plan stage, the NC program check or the stock mesher running, the decision is to end the process, never while anything above is pending, and never while a G-code export runs (counted from Export until it reports, also when no folder is chosen): then the window closes. The app's close decision is one method that the close request carries out, tested case by case: a sign-out pending for 11 s gives delete-and-close, a sign-in save pending for 11 s gives close, an export with blocking work gives close and blocking work alone gives exit, and a refresh in flight gives wait when first asked and 9.5 s later, and close 10.5 s after the first request. After the wait, a refresh still waiting for OpenAI no longer counts as pending, so with blocking work the decision is exit; a refresh in its save is still pending, so with blocking work the decision is close and the save finishes. The delete a timed-out sign-out starts is one method of the app, run within the close request's update, which iced runs inside its Tokio runtime: in a Tokio test, with a signing-out client's refresh held on a /token answer delayed 300 ms, the method takes the client and starts the delete, the refresh then finishes and the store stays empty (checked in review: with the store's plain delete in its place, the test fails with the refreshed sign-in saved again). A close during a refresh shows "Closing when the sign-in refresh has finished (at most 10 seconds)…" and closes on the Tick after it ends. The close request's own call to that method is pinned too: in both timed-out close tests (a sign-out pending alone, and one whose client has a refresh in flight) a sign-in saved before the Close is gone once the entered runtime is dropped after the Tick, which joins the blocking delete (checked in review: with the call replaced by dropping the signing-out client, both tests fail with the sign-in still saved). The process exit itself is not run in a unit test, and neither is the process's lifetime after the wait: a sign-out or sign-in save still pending with blocking work gives close, so the window closes and the app ends when the plan stage, NC program check or stock mesher finishes, as the README says. Found in review (not a test): Cmd+Q (Quit in the macOS app menu) sends AppKit's terminate, which winit handles as the end of its event loop and Iced 0.14 does not pass to the app as a close request, so it skips this decision; the README says that only closing the window waits, and that Cmd+Q does not wait for a sign-out, a sign-in save or refresh, or a G-code export, may lose edits from the last moment and may leave an unfinished sign-out signed in at the next start.
